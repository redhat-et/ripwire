### Changed — `--for` no longer waits on its stamp's git children or reads source files one at a time for clone membership

On a large repo a warm `--for` spent a third of its main thread waiting: the `at=` stamp asked git three questions one after another once the answer was ready (the working-tree status is the slow one), and the clone-membership pass opened every file with a function body, sought to its end and back (a buffer refill of its own on macOS), read it, and normalized its bodies, one file at a time. The stamp is now computed on a worker started right after the index is loaded, so its git children run beside the graph build, and the HEAD and shallow-clone questions are one git child instead of two (when git answers in any other shape, the two questions are asked separately, as before). The clone pass reads each file with one open and one read and spreads the files over up to eight workers; the clone groups are still built in file order on one thread, so every group, member order and `clone=` mark is the one the serial pass produced. `--for` answers are byte-identical, `at=` included (+dirty and +shallow). The MCP server does not prefetch, so a stamp there still describes the tree at each call. New gate `test/forstampprefetchcheck.sh` pins the stamp's shapes against `--doctor`'s, a cache file written inside the tree, a failing and a stalling git, a commit in the middle of an MCP session, and the clone member order.
