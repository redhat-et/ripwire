### Fixed — a history walk no longer downloads, and no longer hangs

- On a long real history, `--for`, `--metrics` and `--exemplar` waited on `git log --name-only` with no limit: past 3600 s on a 310 K-commit ClickHouse clone, and on a blobless clone git fetched blobs from the network as it went (`.git` 15 GB to 33 GB). Now:
  - No git command of ripwire's lazy-fetches on a partial clone: each carries `GIT_NO_LAZY_FETCH=1` (git 2.45 and later) and a closed `GIT_ALLOW_PROTOCOL` (git 2.6.1 and later), as a prefix on that command only. They are not set in ripwire's own environment, so the command `--run-trace` runs, and any other child that is not git, sees the environment you gave ripwire; and the clone of a URL root uses your own `GIT_ALLOW_PROTOCOL` and `protocol.*.allow` as `git clone` would. Versions are from git's source at the tags (`environment.h`, `git.c`, `transport.c`); only git 2.50.1 was run, an older git is simulated by a shim. A verb that truly needs an absent blob says so: `--quality-delta=REF` refuses naming the partial clone and the `git archive <sha> >/dev/null` that fetches it yourself, `--pr-context` lists the changed files from the trees (a dirty tree too) and refuses when it cannot, `--stray-content` reports a branch it could not read as `unknown`, never `merged`.
  - The walks carry `--no-renames`. Rename detection was the only thing that read blobs. It changes one thing: a rename commit now also lists the path it left, which matters only when that path exists again at HEAD (whole history: textual 5 of 354 such paths, hono 3 of 286, tmux 1 of 23).
  - Every record walk has a budget, 20 s or 200 K commits (`RIPWIRE_GIT_WALK_SECONDS`, `RIPWIRE_GIT_WALK_COMMITS`, 0 = none, at most 1,000,000,000; a larger or malformed value keeps the default). A cut keeps the newest commits and says so: `history_unread="1"` on documents with `churn=`/`amp=`, a `history_cut` comment and stderr line on every other CLI verb, and a `_history_cut` envelope note on an MCP answer. Where the clock cut a walk, the prefix it reached moves with machine load, so two runs can differ; the cut is cached until HEAD moves except under `--no-cache`, and a clock cut under about 1,000 commits is not cached. ClickHouse `--for`: 3600 s and unfinished, now 50 s.
  - On a partial clone, no git that scans the promisor pack is started. With lazy fetch off, git parses every object of the promisor pack before it fails on the first absent blob, which is minutes to hours on a clone like ClickHouse (5.2 M objects: `diff --numstat`, `archive` and `log -p` each still running at 90 s). `--pr-context=REF` lists the changed files from `git diff --name-only` there and says so on stderr (a mode-only change is not told from a content change); elsewhere `--numstat` runs under the walk budget, and a stalled or failed one falls back to the same list, which keeps the budget too: if that read stalls as well, `--pr-context` refuses and says so. `--quality-delta=REF` and `--merge-scout` first ask git, without fetching, which blobs of the tree are absent and refuse before `git archive` when any is. `--whereis --with-history` and `--naming-calibration` answer `probed="0" r="partial-clone"` without running `git log -p`, and the rename map behind `--quality-delta` reports a window of 0 commits, truncated. Reads that fail fast on an absent blob still run (`blame`, `show`, `cat-file -e`, a zero-context `diff`, and `archive` when the tree is whole), and a failed one is said, never read as an empty answer:
    - Plain `--quality-delta` on a dirty partial clone used to pass its gate: short-horizon-churn needs the churn window's tree and a blame of the edited lines, and when git refused them the row vanished or read `churn="ambient"`, so the answer said `gating="0"` and exited 0. Now the root says `unread_history=` (`churn-tree`, `churn-blame`, `churn-window` for a window walk cut by its budget, `renames` for a pinned sidecar floor whose rename record was refused), in XML, `--json` and MCP, a row whose blame failed says `churn="unknown"`, and an answer with no gating row exits 6, the partial-answer code, with a stderr line. A dirty `--quality-baseline` there refuses unless `--allow-dirty`, since it cannot tell what it would absorb. A clean tree reads no history and is unchanged.
    - `--slice=SYM:VAR --since=REV` said `status="file_absent_at_rev"` of a file that is in that tree when its blob was not in the clone. It now says `status="unread_at_rev"` (`comparable="0"`) when the tree lists the path, or when the path is not there and the rename record that could reach an earlier spelling was not read.
  - Over MCP, an `owners` call whose history walk was ended by its budget names the budget instead of "no git history".
