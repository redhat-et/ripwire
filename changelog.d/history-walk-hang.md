### Fixed

- **A history walk no longer downloads, and no longer hangs.** On a long real history, `--for`, `--metrics` and `--exemplar` waited on `git log --name-only` with no limit: past 3600 s on a 310 K-commit ClickHouse clone, and on a blobless clone git fetched blobs from the network as it went (`.git` 15 GB to 33 GB). Now:
  - No git child of ripwire's lazy-fetches on a partial clone (`GIT_NO_LAZY_FETCH` for git 2.45 and later, a closed `GIT_ALLOW_PROTOCOL` for git 2.12 and later). A verb that truly needs an absent blob says so: `--quality-delta=REF` refuses naming the partial clone, `--pr-context` lists the changed files from the trees.
  - The walks carry `--no-renames`. Rename detection was the only thing that read blobs. It changes one thing: a rename commit now also lists the path it left, which matters only when that path exists again at HEAD (whole history: textual 5 of 354 such paths, hono 3 of 286, tmux 1 of 23).
  - Every record walk has a budget, 20 s or 200 K commits (`RIPWIRE_GIT_WALK_SECONDS`, `RIPWIRE_GIT_WALK_COMMITS`, 0 = none). A cut keeps the newest commits and says so: `history_unread="1"` on documents with `churn=`/`amp=`, a `history_cut` comment and stderr line on every other CLI verb. ClickHouse `--for`: 3600 s and unfinished, now 50 s.
