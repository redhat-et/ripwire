### Changed — the per-file parse budget counts parser work, not seconds, so a loaded machine indexes the same tree the same way

A file whose parse (or tags query) runs past its budget is read lexically. That budget was wall-clock time (4 s + 1 s per MiB), so a file near the edge was parsed on a quiet machine and read lexically on a busy or slower one: the same tree gave different answers. The budget is now counted in tree-sitter progress steps (500k + 1M per MiB, `RIPWIRE_PARSE_BUDGET=<scale>` still scales it), a number fixed by the file's bytes and its grammar. Measured over the 70,221 files of ten large repositories, the heaviest real file uses 1/9 of its budget; 100 KB of `{` is still cut, in 0.2 s, and 4 MiB in about 2 s. A local tree-sitter patch (`third_party/patches/tree_sitter/002`) makes the query count the sibling scan that made that input quadratic. Wall clock and memory stay only as a backstop far above the budget; when one trips, the warning says the result depended on the machine, `--skipped` rows the file `why="lexical-wall"` or `why="lexical-memory"`, and the next run parses it again. New gate `test/parsebudgetdetcheck.sh`.
