### Changed — the memory limit is also enforced at `operator new`, on by default: a runaway allocation is refused with exit 5 instead of being killed by the OS

The memory guard (on by default at 65 % of min(RAM, cgroup `memory.max`)) read the footprint only between phases, so a single step that grew without bound inside one phase could take the machine down before the next reading. The same limit is now also read at `operator new` (every allocation of 256 KiB or more, and every 64 MiB of smaller ones): an allocation that would pass it refuses the run with one stderr line naming the knob that set the limit, nothing on stdout, and exit 5. One knob covers both lines: `--max-memory` (wins) or `RIPWIRE_MAX_MEMORY`. `RIPWIRE_MEM_BUDGET_MB=<MiB>` sets the allocator line alone and `=0` turns it off. Servers (`--mcp`, `--lsp`), sanitizer builds and `RIPWIRE_ALLOC_COUNT` builds do not arm it. A run that stays under the limit is byte-identical (stdout, stderr and exit code, default map, `--json` and `--for`). On llvm-project with the pre-fix resolver, `RIPWIRE_MEM_BUDGET_MB=9000` refused with rc 5 at a 5,689 MiB footprint before a 3,520 MiB request, inside the class-identity step that held the runaway, where the OS had killed the run before. macOS uses the existing allocator hook; Linux, Windows and macOS with `RIPWIRE_LARGE_ALLOC=OFF` get `src/memceiling_new.cpp`, first proven by CI. A peak the hook cannot see (tree-sitter's own `malloc`) is still disclosed, not stopped. Lane M2 (`fbd3b192d`, `ec810904f`); new gate `test/memceilingcheck.sh`.
