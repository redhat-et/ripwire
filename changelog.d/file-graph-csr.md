### Changed — the file graph's include closure is one flat store, built by a fold over strongly connected components

The file graph's direct edges are now one flat offsets-plus-targets array (`FileAdjacency`), and the transitive include closure is a chunked hybrid store (`FileSetStore`: a presence bitmap and popcount rank per row, each chunk a sorted array or a bitset, whichever is smaller, identical rows shared by hash and verified). On vscode the closure is 3.74 MB where the sorted vectors it replaced were 32.5 MB; on a 100,000-file graph of mean closure 11,098 the process peaks at 580 MB where the rows alone in sorted vectors were 4.4 GB. Answers are byte-identical; `--deps`, `--arch=FILE` and the resolver read the same sets in the same order.

It is built by one fold over the strongly connected components, sinks first: a component's row is the OR of its successors' rows plus their ids, taken back from the store into a single working row, so a file that imports 40,000 modules costs one row and not 40,000 (a first form of the fold held a bitset per imported module: 744 MB against 11 MB at 100,000 files). The fold asks the memory guard as it goes: over `--max-memory`, it stops and says so (exit 5, one line) instead of answering from a partial store, on the graph build and on the second fold `--deps` and `--arch=FILE` run. A payload past a 32-bit offset (8 GiB) is a disclosed stop, not a wrapped offset; that limit was modelled with a lowered bound, not run at 8 GiB.

What it does NOT mean: no answer changes, and no edge is added. `RIPWIRE_TEST_FILESET_CHUNK_BITS` (test only) forces the chunk size on every fold. `bench/FILEGRAPH.md` has the measurements, the forms that lost, and the umbrella shape. `docs/LINEAGE.md` credits the classic closure and bitmap results the store rests on.
