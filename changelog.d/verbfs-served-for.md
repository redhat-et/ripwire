### Changed — a served `--for` no longer re-reads the corpus: the literal scan, the clone pass and the manifest probe answer from a per-index record

On a warm, served `--for`, three passes used to repeat their file-system work on every call: the literal scan read every indexed file, `findClones` re-read every file holding a shared clone key, and the manifest probe `symlink_status`'d three names in every directory. Each now consults its own record in the cache directory (`ripwire-verbfs-<rootKey>-{grep,clones,dirs}-*.bin`) and does the old work only for what the record cannot vouch for: a per-file trigram Bloom filter (a file is skipped only when no pattern of the scan can occur in it and its stat signature is unchanged), the clone groups of an unchanged input digest whose read files are unchanged, and a directory's entry kinds while its own lstat signature is unchanged (links are always probed live). Every answer is byte-identical. Measured on an M5 Pro against fec2ab27c (Release, no PGO, n=5 interleaved, medians): llvm-project 5.02 → 4.00 s (sys 18.6 → 6.6 s; files opened per call 101,664 → 10,416), vscode 1.12 → 0.93 s, envoy 0.80 → 0.67 s; the warm map is unchanged. The cache grows by 70 MB on llvm-project. Armed only where the warm snapshot is (a cached single-root run); `RIPWIRE_NO_VERBFS=1` turns it off; `RIPWIRE_STATS=1` prints one `[verbfs]` line per pass. New gate `test/verbfscheck.sh`.
