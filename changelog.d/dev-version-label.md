### Fixed — a build off a release tag says so in its version (`0.6.10-dev.41+g5593593d3`)

A build of `main` 46 commits past `v0.6.10` printed a plain `0.6.10`, so a bug report, a benchmark rung or an agent's MCP client could not tell it from the release. The version is now a label: exactly `X.Y.Z` on the tag `vX.Y.Z` (`+dirty` with tracked edits), `X.Y.Z-dev.N+g<sha9>` for N first-parent commits past it, `X.Y.Z-dev+g<sha9>` in a checkout with no such tag (a tagless shallow clone), and `X.Y.Z-dev` with no git at all, never the bare release number. `--version`, the MCP `serverInfo.version` (which said `1.0` whatever the build), the LSP `serverInfo.version`, the `--html` page and `--doctor`'s version-mismatch hint all print the same label. Release tag builds are unchanged. Found in the 0.7.0 comparison rehearsal on a fresh M5 machine; `test/versionlabelcheck.sh` pins a tag, a dirty tag, a dev, a tagless and a no-git build, and that every surface agrees.
