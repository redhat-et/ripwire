### Changed — a served `--for` no longer rebuilds the registrar index and the `#include` adjacency on every call

On a warm, served `--for`, two splices of the compact answer rebuilt an index over the whole model for every question: the registrar index behind `<reg>` rows (every registry key with its registration sites, consumers and cut re-export names) and the C-family `#include` adjacency the slot join walks to decide whether a header's `static` is visible from a file. Neither reads the question. Each is now kept in its own record in the cache directory (`ripwire-verbfs-<rootKey>-{regindex,slotjoin}-*.bin`), keyed on the identity under which the warm snapshot serves the model itself (the build's source identity, every option and `RIPWIRE_*` variable, and the content hash of every crawled file), and served only to that model; anything else builds as before, and a build that read a file outside the tree is not kept. Every answer is byte-identical. Measured on an M5 Pro against lane 5b (d76c740fb, Release, no PGO, n=5 interleaved, medians, served warm `--for`): llvm-project 3.85 → 3.52 s (user 3.70 → 3.38 s; the two splices 408 → 142 sampled ms), vscode 0.90 → 0.88 s, envoy 0.63 → 0.61 s; the warm map, peak RSS and every answer are unchanged. The cache grows by 0.8 MB on llvm-project and 72 bytes on vscode and envoy. In a plain (non-release) build every served index is also rebuilt and checked equal, so a later change that edits the model after ingest cannot serve a stale one unnoticed. Armed only where the warm snapshot is; `RIPWIRE_NO_VERBFS=1` turns it off; `RIPWIRE_STATS=1` prints one `[verbfs] slotreg` line per index. New gate `test/slotregcheck.sh`.
