### Changed — MCP tool failures are `isError` results that name the next call; tools carry `title` and `idempotentHint`; parameter descriptions say what a parameter means

- **Tool-execution failures are results, not JSON-RPC errors (MCP 2025-11-25, SEP-1303).** A tools/call that names a tool this server serves and then fails inside it (a missing or bad argument, a business-logic refusal) now answers `result.isError: true` with the same sentence in `content`. Clients SHOULD show those to the model; a JSON-RPC error is one they MAY drop. An unknown or `--mcp-tools`-hidden tool, a missing or wrong-typed `name`, a wrong-typed `arguments` and an unknown method stay JSON-RPC errors, and so do the server faults (`-32000` memory hard line, `-32601` remote edits off, `-32603` internal). A not-found that carries the CLI's `found=0` document (find_symbol, find_referencing_symbols, impact, uses, path_between) is an answer, so it is a plain result: the document first, the refusal sentence beside it (it was `error.data.answer`).
- **Every refusal names the ripwire call to make next** (Xu & Wu, 2609.35381: a step naming a server tool raised recovery to 84-88%, a terminal command left 45%). The sentence ends in `— next: <tool> field="value"`: the same tool with the table's example for a missing, bad or undeclared field; the near-miss for a not-found that has one (an edit verb names `find_symbol` first, never a placeholder edit); `grep pattern=` the spelling for one that has none. `test/mcpnextcallcheck.sh` round-trips every next call.
- **`title` and `idempotentHint` on every tool.** The two inserts are the only tools that are not idempotent.
- **Parameter descriptions say what a parameter means.** `path` is the absolute repo root and defaults to the launch root; `limit` is rows per page; the type stays in the schema's own `type` key, and the bad-value refusal names it.
- **Each tool description opens with the moment to use it**, since a deferred tool search reads the first words.
