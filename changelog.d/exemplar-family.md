### Added — `--for` on an add-a-new-X task names X's family: the existing siblings a new one joins

A task like "add a new builtin scalar SQL function", "I need to write a scheduler plugin that lives in the tree" or "I want to add a new dialect" now ends with an `<exemplar_family>` block before `</ctx>`: how the existing X are grouped (`rule=`: implementors of one base or interface, the entries of one registry map or dispatch table, typed instances of one C/C++ struct type, items under one attribute macro or decorator, or names ending in X in one directory), the shared `key=` and where it is defined, the directory the family was narrowed to (`scope=`), its size (`n=`, test code excluded) and up to four members, the typical one first (nearest the median size). Go registries and C vtable instances are found even where the implementors list is empty (Go has no `implements`; a C `const MeterClass X_class` is not a subclass). The block is present only when a family resolves, the answer before it is unchanged, a token budget holds it (`held="budget"`), and the MCP `for` tool prints the same element. New gate `test/forexemplarcheck.sh` pins one fixture per rule (C typed instances, Go and C++ registry maps, a Rust attribute macro, a TS interface, a Python subclass), the wordings that fire and the ones that stay silent.
