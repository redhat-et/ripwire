### Fixed — a Python call through a from-imported submodule is a call

`from . import mod; mod.f()`, `from pkg import mod`, `from pkg import mod as m`, `from .sub import mod` and `from .. import mod` now bind `mod.f()` to the module-scope `f` of that submodule, the way `import pkg.mod as mod` already did, so `--callers`, `--impact` and the map count these callers instead of reading zero. Before, such a call was read as a call outside the tree (external=). The binding is used only when nothing else may bind the name: the package's own namespace (a def, assignment, import of another file, star import, module `__getattr__` or `globals()` write), a rebinding in the importing file (including a star import placed after the from-import whose module binds the name, or any star import of a module outside the tree placed after it; a star import placed before counts too when the from-import sits under an `if`, `else`, `try`/`except`, `with` or loop, since that from-import may not run), or a second import of the name to another module each leave the call unproven, and an unproven call is declined and counted (declined_calls=), not picked. A submodule that writes its namespace dynamically, star-imports another module, or defines `f` only under an `if`/`try`, withholds the call too, and so does any second module-scope binding of `f` there (a later `f = g`, `del f`, or `from _speedups import f`, plain or under `try`). When both `p/mod.py` and `p/mod/__init__.py` exist, the package is the module, as in Python. A from-import inside a function binds a local only, so it neither proves nor contests the module-level name. A local or parameter named like the module is never the module. Not read yet: a package that re-exports `f` from another file (declined), and `pkg.mod.f()` written in full. Also not read: an `if TYPE_CHECKING:` guard, so `if TYPE_CHECKING: from p import mod` with `else: import p.mod_rt as mod` binds `mod` to two files and the call is declined and counted (before, the runtime import was picked). Known limits, still proven though Python binds otherwise: a submodule that writes `vars()['f'] = g` or runs `exec('f = g')` at module scope, and a package that assigns `sys.modules[__name__ + '.mod']` to another module. The module form `import pkg.mod as mod` followed by a star import that binds `mod` is read as before (proven).

### Changed — `--for=path from A to B` keeps the path's own rows in the ranked head

In a task that asks `path from A to B` (opening with `path from`, or `trace`, `show`, `explain` or `what is` then `the call path from`, `the code path from` or `the execution path from`, and not also asking `who calls` or `callers of`), a ranked caller of A (a resolved call, not a by-name one) that A does not itself reach through resolved calls is upstream of the asked path. It is scored below every other row, keeping its own order; files_first may still list a file's best row early. The header says how many moved (`[path from: N callers of the from endpoint scored below the path's own rows]`); pack-task prints it as its own comment, so the compact legend keeps it. A caller of A that A reaches at any depth stays (recursion, an eval loop), and so does B itself. A's reach walk stops at 4096 symbols, and then nothing moves (`path_from_capped=1`). B need not name a symbol. Before, a newly bound caller of A (`python -m django`'s `management.execute_from_command_line()`) could push a hop under A past the 40-row head. The MCP `for` and pack-task twins apply the same rule.
