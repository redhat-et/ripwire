### Changed — a warm run no longer holds extra copies of the cached facts

A warm run used to decode every cache record into one path-keyed map before the parse workers started, move each file's facts into a worker's arrays and move them again in the merge, so the parse-pool join held up to three sets of fact arrays. On envoy that put the warm `--deps` peak memory footprint 45 % over the cold run that wrote the cache. Now the cache load reads only each record's head (its key, hash and family counts), and the parse worker that takes a hit reads that one record, checks its checksum and key, and decodes it straight into its own arrays. The merge moves one fact family at a time and frees each worker's array as soon as its rows have moved. On envoy the warm peak drops 37 % and sits 3 % under the cold one; the answers are byte-identical to a cold run and to `--no-cache`. A record that fails its read, checksum, decode or key check in the worker is parsed from source after the pool joins, so a torn or colliding record still costs only time. The cache format moves to 49 (the record head gains the eight family counts), so an older cache is rebuilt once. New gate `test/warmpeakcheck.sh` pins the warm peak against the cold one.
