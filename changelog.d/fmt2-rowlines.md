### Changed — a `--for` answer serves its `<sigs>` and `<tail>` rows as text lines, and sequential ranks are not spelled

On the answer-first `--for` answer (the CLI default: paged, `--page-bytes=0`, `--signatures-only`, or under a `--token-budget`), the rows of `<sigs>` and `<tail>` are text lines in ONE CDATA per section instead of one element per row, and a `<sigs>` row whose rank is the previous row's + 1 does not spell `r=` (`<sigs … rseq="1">`). A `<t p=P sym=SYMS/>` row is the line `P SYMS` (other attributes follow, tab-separated); a `<d l=L e=E n=N p=P …>SIG</d>` row is `P:L-E N k=v.. | SIG`; a row the line grammar cannot give back exactly (one that quotes a `<doc>` comment, for instance) stays verbatim XML on its own line, starting with `<`. The answer's legend defines both in two clauses, last before `</ctx>`; both are legend-dictionary entries, so `--legend-seen` leaves a held one out. The answer is still well-formed XML and a newline appears only inside CDATA (G4, owner ruling 136).

It is lossless and it is the last step: every row, attribute and byte of text is recoverable (`test/rowlines.py` decodes an answer back to its element form byte for byte; `test/rowlinescheck.sh` (L1) pins that against the `RIPWIRE_NO_ROWLINES=1` twin, with mutation negative controls), ranking, paging and the budget fit read the rows as elements exactly as before, and each page is encoded after it is cut, so a page holds the rows it held. Measured on 89 dev questions against the parent binary: the decoded answer is identical on 89 of 89 (whole answer and page 1), page 1 is a median 1,274 B = 7.7 % smaller, and the three orientation rungs are unchanged (0 cells up, 0 down). The format's source lane measured the same encoding at a median 743 + 113 Claude tokens per page-1 answer (n=15, one model).

What it does NOT mean. `est_tokens=` and the page size still count the element form, so both are upper bounds on what is served, and page 1 does not yet use the freed bytes for more rows. Whether an agent reads a line row as well as an element row is NOT established: the comprehension probe is specified and not yet run. A consumer that parses rows as elements (`xmllint --xpath`, a script) must decode first or set `RIPWIRE_NO_ROWLINES=1`; 0.6.x answers are unaffected by the decoder (it returns an element-form answer unchanged). Not applied to `--legend=first`, `--json`, or MCP `for`.

### Changed — the edit-routing line `ripwire wrap claude` writes no longer says a Read is always required before an Edit

Claude Code refuses a native Edit on an unread file only when the file is outside its working directory (measured on stored sessions: 4 refusals in 283 Edits, all outside the session directory; 7 unread in-directory Edits, all accepted). The blurb now says so: a body ripwire delivered is the verbatim text of its lines and is edited directly inside the working directory; a ranged Read is for what was not delivered, and always for a file outside it. Other agents' text is unchanged. This changes no answer byte; its effect on agent behaviour is UNTESTED. Re-run `ripwire wrap claude` to refresh an installed copy.
