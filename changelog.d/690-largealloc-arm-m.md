### Fixed — `largeallocpeakcheck` arm M no longer depends on how fast the machine is (#690, thanks @jflowers)

Arm M checks that `--max-memory` sees the pages the macOS large-block route hands out. It set the limit to half the routed peak, with a 256 MB floor, and expected the run to stop. Since #648 `--deps` builds no graph, so the hard line after the graph build no longer saw a reading over that limit. The run stopped only when the guard's 5 s cadence happened to take a reading during the parse. @jflowers bisected the failure to #648 on an Apple M5 Max, where the run takes about 1.7 s, and diagnosed it: every reading the guard takes on such a run (at ingest start and after the ingest) sat under 256 MB, so the run finished over its limit and disclosed that, as arm D expects. Our M2 passed only because it was slow enough to get a reading during the parse.

The arm now sizes its limit from the reading the guard takes on every run, right after the ingest. One unlimited run with `RIPWIRE_STATS` reads it (`[mem] phase=model`). The limit is set a quarter below it, and the capped run must exit 5 with nothing on stdout and the guard's own line naming that limit. The arm prints the reading and the limit. It fails, never passes, when the reading is missing, does not hold the routed reference array, or the limit is not below it. The capped run is checked twice: once with the allocator line off, so the guard's hard line is the one tested, and once with it on (default). Test-only: no source change.
