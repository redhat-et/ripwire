### Changed — a `--for` task with no table or registration word still reaches a registration row

The table block that ends a `--for` answer (`<lit shape="table">`) used to need a word such as register, table, default or handler in the task. A bare subject (`new_boxed_executor for HashJoinNode`, `light.turn_on hue async_turn_on`) has none, so the block never ran. Now such a task runs the same walk over its backticked spans and identifier-shaped words, but lists only strong rows: an argument of a registration call (`reg=`), a top-level macro or call row (`tbl="item"`), or a row of a macro table (`for_all_params! {`, `$macro! {`). A dict, list, `__all__`, `#define` or const-array row, and a site that is no row, is weak: counted in `weak=N`, never listed; with no strong row the answer is unchanged. A task with no identifier-shaped word and no backticked span scans nothing. The legend clause that says this rides only on such an answer.

The callee names that count as a registration are narrower: `use` is no adding verb (it is the prefix of hooks such as `useRouter`), the noun after an adding verb must be the name's last word (`addEventHandler` is one, `addCommandLineOption` is not), and `reg` is a verb only as the last word or right before route, command or handler (`async_reg`, `reg_handler`; not `reg_value` or `reg_field`, a hardware register). The table legend is shorter: it no longer lists the vocabulary or the ranking of generated files, says the registration call is looked for 4 lines and 512 bytes above the site, and the `tail=` sentence rides only beside a `tail=`.

Gate `forregrowcheck` covers bare subjects on Rust, Python, Go and TypeScript fixtures, a weak row beside a strong one, weak-only rows of four kinds (each answer byte-identical with the block switched off), the no-call shapes, and the vocabulary cases above with their twins.

What it does NOT do: it does not list a weak row for a task with no cue word, even when that row is the answer; ask with a table or registration word for those. A callee's name is still no proof the call registers.

### Changed — a `--for` excerpt shows the match arm or case that holds the literal; `body="above"` only when the body was printed

An `<x>` excerpt in the `<lit>` block shows one window around each site, from the line before it. When that window leaves out the head of the match arm or case holding the site, the window now starts at that head, at most 12 lines up, and the excerpt says `arm="1"` (a legend clause rides only with it). Arms are an allowlist: a Rust, C# or PHP `Pattern => {` with balanced parens (never a JavaScript `x => {` callback), a `case` or `default` label (C, C++, Java, JavaScript, TypeScript, Go, C#, Swift, Python `match`), a Python `elif` or `else:`, a Ruby `when`, `elsif` or `else`, and an `else if` or `else` branch in C-family and Go code. Openers the window already shows (an `else {` right above the site) are passed over to the arm above them; an `if`, a loop or a function above the window ends the walk with the old window. Measured on risingwave-02 (all three wordings): the window of `handle_alter_streaming_rate_limit` now starts at the `(Table, Source) =>` arm and holds the field read that picks the throttled id.

A `<ls>` row said `body="above"` when its owner's line, path and name appeared anywhere after the ranked rows, including a hop row (`<h>`) whose body the fold skipped. It now says so only when the answer printed the owner's whole `<b>`; a hop row, a fold skip or a truncated `<b>` that stops before the site is no body above, and the block serves its own excerpt.
