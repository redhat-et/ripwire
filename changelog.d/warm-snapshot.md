### Changed — a warm run on an unchanged tree loads the crawl, the model and the resolved graph instead of rebuilding them

A warm run used to skip only the parse. It then walked the tree again, asked git for its ignore answer again, decoded every cache record, rebuilt the model and resolved every reference: all of it a deterministic function of what the cache already held. A run now stores that outcome **as a section inside the cache file itself**, once the tree has been parsed and is unchanged, and the next run on the same tree reads it back instead of recomputing it.

**This bumps the index format, so every existing cache file is rebuilt once.** The cache header grew to carry the section's offset and length, which moves every record offset, so a cache written by an earlier ripwire is refused and re-indexed — one cold run per tree, after which runs are warm again. `--doctor`'s `index-cache` row names the refusal (`lean="format-version"`) if you want to see it happen. Nothing is written beside the cache file: the file you name with `--cache=` is still the only file that appears.

Measured on the flagless map against `--cache=FILE`, median of 5, `/usr/bin/time -l`, dev build, macOS arm64. Both columns are the **same binary**, the "before" column with the feature disabled (`RIPWIRE_NO_WARMSNAP=1`), so nothing in the comparison turns on which build produced which number:

| repo | wall before | wall after | user CPU before | user CPU after | instructions before | instructions after | peak footprint before | peak footprint after | cache file before | cache file after |
|---|---|---|---|---|---|---|---|---|---|---|
| cpython | 1.33 s | 0.18 s | 1.47 s | 0.25 s | 21.82 G | 2.51 G | 382.5 MiB | 297.9 MiB | 151.6 MB | 228.4 MB |
| envoy | 1.25 s | 0.16 s | 1.32 s | 0.17 s | 20.26 G | 2.28 G | 334.7 MiB | 258.8 MiB | 154.6 MB | 217.4 MB |
| vscode | 3.36 s | 0.28 s | 3.57 s | 0.34 s | 53.66 G | 3.94 G | 591.5 MiB | 458.8 MiB | 284.6 MB | 397.2 MB |

**What it costs.** The cache file grows by exactly the section — 40 % to 51 % on those three trees — and the one run that writes it is slower and larger than a run without it (envoy 22.24 G instructions and 382.5 MiB against 20.26 G and 334.7 MiB). That run also rewrites the whole cache file rather than appending to it — 217 MB on envoy, not just the 63 MB section — though the records inside are copied forward unchanged rather than re-serialised, and the file is published by rename, so a cache file is never modified in place and an interrupted write never reaches it. What that rewrite costs in wall-clock I/O on a slow disk is not measured. Warm **peak memory falls** about 22 % on all three trees. A cold run's peak rises, measurably on some trees, because the crawl records what it looked at.

The run after an edit writes nothing: only a run that re-parsed no file stores anything, so no run pays both a cache write and a section write. An edit therefore leaves the cache file carrying **no** section at all, which is also how the stored outcome is invalidated — there is nothing stale left to refuse.

**What it never does is answer from a section it cannot vouch for.** The section carries the build's source identity, a digest of every option and of the environment the crawl and the resolver read, and one checksum over every byte. The model and the graph are keyed on every crawled file's path and content hash, and the graph on every file the resolver read outside the cache (a `go.mod`, a Cargo manifest, a `tsconfig.json` above the root). The crawl is replayed only while every directory and every entry the walk looked at still has the device, inode, size, mtime and ctime it had, every input of git's ignore answer is unchanged, and none of them was younger than two seconds when it was recorded. Any mismatch is a full run, and the answer is the one that run always gave.

`test/warmsnapcheck.sh` holds it: stdout of a loading run is byte-identical to a `--no-cache` run for 23 verb invocations over every fixture tree in `test/`, and a changed file, an added or removed file, a same-size edit with its mtime put back, a new subdirectory, a changed `.gitignore`, a file added under a directory git reported ignored, a changed `go.mod`, a removed cache file, another `--exclude` set, a patched version field, a flipped byte and a section truncated inside a field each refuse it. The damage arms leave the cache file otherwise valid and check that its records are still served, so each one proves the section's own guard refused rather than the cache reader.

Not served: a multi-root run, `--scip`, `--pin-census`, `--max-memory`, `--no-cache`, a single-file root, and, for the model alone, a tree holding a pdf/docx/pptx/xlsx when `markitdown` is installed or one of them has a cached extraction (the crawl and the graph are still served). `RIPWIRE_NO_WARMSNAP=1` turns it off; `RIPWIRE_SNAPSHOT_STATS=1` prints one stderr line saying which stages a run loaded and which guard refused the rest.
