### Added — a `--for` answer names the ranges to read next, in one line: `<act read="path:l-e,…"/>`

A `--for` answer (CLI, every posture, and MCP `for`) now carries, right after its `<sigs>` (after the key-body group when one follows it), one element listing the line ranges of its top 3 ranked `<sigs>` definition rows: `<act read="src/a.py:10-42,src/b.py:7-19,src/c.py:88-101"/>`. The answer's legend defines it in one clause (a legend-dictionary entry, so `--legend-seen` and an MCP `legend="ref"` session leave a held one out): read them all in ONE turn of parallel ranged Reads, never whole files, except a body the answer already serves, and search only for what no row lists. The line is written only when every one of those rows carries both `l=` and `e=` — a list with a hole in it would send an agent searching for the hole — so an answer whose top rows include a markdown heading (no end line) carries none. It reads the ranked rows only: the fold, the body slot and the page size never change it. It is a block of the answer's row stream that no page counts, so a page ends at the row it ended at without it. Under an explicit `--token-budget` (or MCP `budget_tokens`) it rides only while the answer still fits the budget with it, so a budget the answer fits returns the unbudgeted answer byte for byte. `--legend=first` carries the same line, its clause in the leading legend. Not on `--json`. `est_tokens=` rises by the added bytes, an upper bound.

Why: agents acting on a `--for` answer were measured reading the ranges it listed one request at a time (1.02-1.27 calls per request), each request re-sending the whole context. Batching those reads is a MODEL estimate of a 7.6 % cut of the tokens to the first edit (14 % on tasks only ripwire answers); it is not yet measured in a live session. Measured on 89 dev questions (page 1): 87 answers carry the line, 3 ranges each, a median 119 B for the element; the orientation rungs (file, function, body) are unchanged on all 89, and no page-1 row moves.

The edit-routing line `ripwire wrap` prints, the subagent brief block, the SubagentStart note and the orient skill now say the same thing: read every listed range in one turn, ranged.

`RIPWIRE_NO_ACTLINE=1` turns it off (the answer is then byte-identical to the answer served before this change); `ripwire --version` says which (`act=on|off`). Gate: `test/actlinecheck.sh`.
