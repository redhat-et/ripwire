### Fixed — one build writes one warm snapshot, however its parse pool was scheduled

Two runs of one build on one tree could write different warm-snapshot bytes. The parse pool merges each worker's rows, and the order in which workers draw files is the work-stealing schedule's. The model build re-sorts most families after the merge, but three it kept as merged: includes, Ruby constant opens, and `--quality-delta` construct hits. Their order, and the snapshot's MODEL section with it, changed from run to run (C1-KEYFIX, #751, saw a permutation of the same rows on 8 of 8 trees). They are now put in fileId order once, after the merge, with a stable sort, so one file's rows keep the order its worker emitted them in. Every other per-file table already had that order. Three model-build sorts whose keys left a field out now key on every field: FFI binding aliases (`lowConf`), route registrations (handler name), and client route calls (line, method).

`RIPWIRE_PARSE_THREADS=<n>` (1 to 256) sets the parse pool's worker count, and the `RIPWIRE_CACHE_STATS` line now reports it as `parse_threads=`. The knob exists for the gate. It does not enter the snapshot's options key, so a one-worker recording and an every-core one name the same file.

Measured on a 3,230-file fixture corpus, ga-libzmq-02 and ga-sinatra-01, and ga-black-01 under `--quality-delta`: a one-worker recording and an every-core recording are now the same bytes, with only the write stamp and its checksum masked. Before the fix, two every-core runs differed. `test/snapdeterminismcheck.sh` holds both cases: one worker against eight, two every-core runs, the whole file, and the decoded families in fileId order with a nonzero row count.
