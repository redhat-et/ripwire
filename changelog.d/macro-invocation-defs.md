### Fixed — a C/C++ macro invocation is no longer stored as a function definition

tree-sitter cannot expand a macro, so an invocation written where a declaration may stand parsed as a typeless function declarator: `REGISTER_FACTORY( F, B ){ "name" };`, a class-member `MOCK_METHOD( … );` or `DECLARE_LUA_FUNCTION( C, f );`, `FALSE_RUNTIME_GUARD( x );`, an in-function `ASSIGN_OR_CO_RETURN( auto e, co_await f() );`, a C run of `EXPORT_FUNC( name )` lines. Each became a function definition named after the macro: 4,808 on envoy and 391 on cpython (0 on tmux, ninja, htop, cockroach and vscode). Beyond the phantom rows, they made the macro's name non-unique, so its real invocations never became `role="macro"` uses and an in-tree `#define` read `in="0"`: envoy's `REGISTER_FACTORY`, invoked from 573 places, had no caller (now `in="442"`, ten phantom definitions gone). Now such a site mints no definition and is a use of the macro. A block-forming macro whose braces hold statements right after its own `( … )` (`TEST_F`, `TARGET`, `WASM_EXPORT`) keeps its definition, as do real ALL-CAPS functions and constructors; no other name lost or gained a definition on the seven repos. Trailing annotation macros (`void f() ABSL_EXCLUSIVE_LOCKS_REQUIRED( mu ) { … }`) are unchanged and still a known gap. Caches rebuild once (parser version bump).
