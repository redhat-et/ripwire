### Fixed — `from pkg import mod` is a file edge to `pkg/mod.py` (thanks @jflowers, #478)

A from-import's one dependency record names the package (`pkg`, `.`, `..`, `.sub`), so the file graph had an edge to `pkg/__init__.py` and none to the submodule a member names: `from pkg import mod` lost `pkg/mod.py`, and `from . import sibling` lost `./sibling.py`. `--deps`, `--arch` Ca/Ce, cycles, `--impact`'s importer tier and every other view on the file graph now also carry an edge to the module `<package>.<member>` names, resolved exactly as `import pkg.mod` is: same roots, and no edge when no file or two files match. The member is the name taken from the package, never the local alias (`from pkg import mod as m` reaches `pkg/mod.py`, not `pkg/m.py`); `from pkg import SomeClass` with no `pkg/SomeClass.py` adds nothing, and `from pkg import *` adds nothing. A namespace package (no `__init__.py`) gets the member edge although the package itself resolves to no file.

What it does not change: the call graph. A member edge is a dependency, not evidence for a bare call, since `from pkg import mod` makes no name of `mod` visible unqualified, so call binding (Rule 3) is byte-identical. The edge is drawn whenever the submodule file exists, including when `pkg/__init__.py` also binds that name; the import still loads the package, and that binding is usually the package re-exporting its own submodule.
