### Added — `--for` names the implementations that can run at an interface call the task names

When a name-exact `--for` task names a function and a member call inside it (`Parser::Load file_reader_->ReadFile`, `MDBook::execute_build_process renderer.render`) and that call goes through an interface, trait or abstract receiver the resolver declined, the answer now carries `<dispatch call= in= p=file:line cands= shown= test=>` after the caller hop: one `<s>` row per in-tree implementation that can run there (`ctor=` rows name where that type is made), and, when exactly one production candidate is left, its body. Test doubles (test code, or a type only test code names) are counted in `test=` and not shown; a type that production code builds — in a registry, a factory with a production caller, a file-level registrar, `main`, a Go `init`, or a C/C++ OS entry (`wmain`, `_tmain`, `WinMain`, `wWinMain`, `DllMain`) — is never counted as a double. When the task writes a receiver (`disk_->ReadFile`), only a site with that receiver answers. Languages that type structurally carry `floor="1"` (an unlisted type can still run there) and never get a single body. Default regime and XML only; `RIPWIRE_NO_DISPATCH_HOP=1` turns it off; answers whose task names no such call are byte-identical. On ninja's "Parser::Load file_reader_->ReadFile" the answer now prints `RealDiskInterface::ReadFile`'s body (the test file system is counted as a double); on mdbook's "renderer.render" it lists the four production renderers and where they are built.

Not covered: a task that writes the TYPE as the receiver (`Disk.ReadFile`) or a reference alias of the field gets no element. On an index the memory guard cut (the MCP `for` answers over one; the CLI refuses it), a type no kept file builds is not counted as a double, because the cut may have dropped the file that builds it; only a definition on a test path is demoted there.
