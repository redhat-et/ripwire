### Changed — a C++ member written as a smart-pointer alias, and a Rust local filled by a trait-object call, hand an interface-typed call to the dispatch tier

A C++ member written `Http::FilterSharedPtr handle_;` (`using FilterSharedPtr = std::shared_ptr<Filter>;`, a `typedef` of `std::unique_ptr<Filter>`, or up to three plain aliases of such an alias) is read as its pointee through `->`, exactly like a member written `std::shared_ptr<Filter>`: an interface pointee declines `gate="iface"` with its implementors counted, in place of every same-named method as a `via="name"` guess. A Rust `let d = s.get_decl( id ); d.run()` whose one proven callee returns `&dyn Command`, `Box<dyn Command>` or `impl Command` types `d` the same way, and an inherent method of another type that happens to be called `run` is no longer listed.

The alias must be in scope where the member is written: its own class, an enclosing namespace or class, or the namespace the member's qualifier names. A template parameter that shares an alias's name, a name that is not visible there, an alias that is also a class, two same-scope aliases that disagree, a pointee written in `std`, and an alias of a concrete class whose virtual methods derived classes override all keep the by-name rows; a deleted or defaulted operator, a `friend` declaration or a member-template declaration never makes a class an interface.

Floors, stated: a using-directive (`using namespace x;`) is not followed; a using-declaration of the alias's name in a nearer scope than the alias is not seen; a Rust `type` alias of a class-like name in a mixed C++/Rust tree can stop an unrelated C++ alias from peeling (the base rows stay); a local or parameter written as an alias is not peeled; Go interface-typed results are not read.
