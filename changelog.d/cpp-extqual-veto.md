### Fixed — C/C++ call edges read the include roots, and a call qualified by a namespace the tree never defines stays hedged (#478, thanks @jflowers)

The C-ROOT-INCLUDE change (#524) gave C/C++ trees their include-root file edges but kept the call narrow on the includer-directory closure, because coupling them bound about 300 Envoy calls to a wrong in-tree namesake without a hedge. The call narrow's include-file rule (Rule 3) now reads the root edges, behind two vetoes. First, a C/C++ call qualified by a name the tree never defines (no class, struct, alias or namespace of that name in any definition's scope or member path) takes no include proof: `absl::Span(…)` no longer binds Envoy's own `class Span`, and `fmt::ptr(…)` no longer binds `OptRef::ptr`. The pick keeps the existing `via="name"` hedge. Second, a `std::f(…)` call must name a member of namespace std itself, so `std::format(…)` never binds the `format` member of a `std::formatter<…>` specialization. Member calls keep the includer-directory closure, both for the receiver's class and for the include-file hedge, so a header only the root probe reaches no longer spreads `factory->isTerminalFilterByProto()` over its three factory classes. A bare call whose file declares `using ext::make;` with `ext` foreign is hedged the same way as `ext::make(…)`. A header that holds a prototype and an `#else` `static inline` stub of one C function no longer pins the stub over the real definition in a `.c` file (htop `Demangle_demangle`); the call keeps its split.

Measured on Envoy (site dumps, hand read; the method is the one #478's Ca/Ce measure motivated): 2,819 call sites gain an unhedged bind against the decoupled build, and a hand sample of 30 of them is 29 right. Without the vetoes the same coupling was 18 / 30, and all 156 calls qualified by `absl`, `fmt`, `nostd`, `grpc`, `testing` and the like were wrong; the vetoes remove all 156. On htop, `Machine_new → Machine_init` gains on nine platforms through the root `Machine.h`, all right; ninja is unchanged. On ClickHouse, 122 sites gain (about 121 right), and 183 wrong binds drop: `std::find(…)` and `std::string_view(…)` had bound a polyfill `namespace std { struct string_view }` that only one file includes. Answers, against main with the same arguments: of 61 graded C/C++ questions (Envoy, htop, tmux, ninja), 50 are byte-identical; the 9 graded ones that change keep their tier and their credited items, and none loses one. Of the 60 stored practice questions, 59 are byte-identical and one (ClickHouse) moves only a counter.

What it does NOT fix: a qualifier the tree does define but that aliases an external namespace (Envoy's `namespace Protobuf = google::protobuf`, so `Protobuf::Map` binds an in-tree `Map`): about 37 Envoy sites, because C++ namespace aliases are not recorded yet (so `namespace M = mine; M::f()` also stays hedged). It also does not fix the right typed-receiver binds the second veto gives up (about 44 on Envoy), a `using namespace ext;` directive (a bare call under it can still bind an in-tree namesake), or a foreign root over an in-tree inner segment (`ext::ns::f()`, where only `ns` is read).
